# Requirements

Write requirements as a table with columns **ID** and **Requirement**. A document type may add columns needed for its own analysis. Use stable IDs (R1, R2, ...); never reuse a removed ID.

Each requirement states a distinct required outcome or behavior in terms that can be checked, including the relevant conditions and boundary cases. Keep implementation choices in the approach, and mark requirements awaiting a decision using [Plan Decisions](decisions.md).

Map acceptance criteria and verification checks to the relevant requirement IDs or constraints, and map requirements that necessitate a change to inspected or new targets. In dual, put requirements in `what-to-do.md` and their implementation and acceptance checks in `how-to-do.md`.
