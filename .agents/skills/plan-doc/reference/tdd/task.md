# TDD 阶段任务流程

本阶段根据已确认的产品需求设计系统实现。TDD 指 Technical Design Document（技术设计文档）。

## 执行步骤

1. **确认需求基线**
   - 查找相关 PRD、评审记录和用户提供的需求说明，确认版本、状态和未决项。
   - 用已确认的需求编号作为设计输入。PRD 为草稿时，TDD 也保持草稿；未决产品问题不能当成已批准要求。
   - 没有 PRD 时，只有在需求说明已讲清问题、预期结果和范围后才继续；否则先完成 PRD 阶段的信息收集。
   - 审查 TDD 时，先确定审查范围和文档版本。

2. **检查现有系统**
   - 阅读仓库指引、模块说明、接口契约，以及与需求相关的实现、调用方、数据模型、配置、迁移、测试和部署约定。
   - 跟踪需求涉及的调用链和状态变化，记录文件、类或方法、接口、表或字段、配置项等证据。
   - 区分代码事实、用户提供但未验证的信息、推断和未知项。静态代码不能证明运行时、数据库或外部服务行为。
   - 除非用户明确要求，不修改代码、配置、数据或测试。

3. **映射需求与系统边界**
   - 将每项需求关联到设计对象和验证方式。
   - 列出本次涉及的功能、模块、接口、数据和部署范围，并标明验收边界。
   - 区分通用能力和目标专有能力。先检查接口、策略、适配器、工厂、注册表、配置和事件等扩展点，再判断是否需要修改通用能力。
   - 现有扩展点无法满足需求且有缺口证据时，才设计通用能力变更；同时说明受影响的调用方、兼容影响和最小变更范围。

4. **形成技术设计**
   - 选定有证据支持的主方案，说明组件职责、依赖方向、数据流和边界。
   - 按需说明数据、配置、接口、事件、状态、校验、幂等、并发、事务、超时、重试、异常、权限、日志和指标。
   - 对重要分支写清条件、动作和结果。多组件、跨服务、异步、回调或状态竞争流程用 Mermaid 时序图；简单流程用文字或表格。
   - 只列出会改变设计的未决选项；建议不等于决定。

5. **安排验证与交付**
   - 为每项需求指定验证层级、对象和通过标准。
   - 记录部署、迁移、兼容、回滚和监控要求。未知的发布窗口或操作权限列为开放问题。
   - 列出实施阶段要新增或修改的对象，不展开为逐步编码指令。

6. **处理设计决策**
   - 只追问会改变组件边界、公共接口、数据结构、兼容、安全、性能预算或验收方式的选择。
   - 一次问一个问题，并说明代码证据、可行选项和影响；AskUserQuestion 可用时通过该工具提问。
   - 用户确认后，将结论写回设计并更新决策记录。未确认项注明影响和阻塞内容。

7. **起草或审查 TDD**
   - 开始起草或审查前读取同目录的 `document.md`。只做需求确认、代码检查或技术分析时不加载。
   - 检查需求、设计、图表、变更对象和验证方式是否对应。
   - 按 `SKILL.md` 的路径规则保存，并说明未决项。

## 完成条件

每项已确认需求都关联到设计和验证方式。关键数据、接口、流程、失败结果及兼容影响均已说明，或列为开放问题。代码事实注明来源；没有实现或运行验证的内容，不写成已完成。
