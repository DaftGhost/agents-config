# PRD 与 TDD

PRD 写清目标用户遇到的问题、预期结果、本次范围和验收方式。TDD 根据已确认的 PRD 需求设计系统实现和验证方案。TDD 指 Technical Design Document（技术设计文档）。本 skill 用于创建或审查这两类 Markdown 文档。

## 选择阶段

- 梳理想法、分析需求或编写、修改、审查 PRD：进入 PRD 阶段，只读取 [PRD 任务流程](reference/prd/task.md)。
- 设计技术实现或编写、修改、审查 TDD：进入 TDD 阶段，只读取 [TDD 任务流程](reference/tdd/task.md)。
- 同时要求 PRD 和 TDD：先完成 PRD；进入 TDD 时，以 PRD 中已确认的需求为基线。
- 用户只要口头建议、任务拆分或直接改代码时，按请求处理，不创建 PRD 或 TDD。

## 渐进式加载

进入阶段时只读当前阶段的 task.md，不加载另一阶段的文件。task.md 说明本阶段要做什么、何时完成；准备起草或审查文档时，再按它的指示读取同目录的 document.md。document.md 规定文档结构和评审标准。完成 PRD 后，继续编写 TDD 时再读取 TDD 阶段文件。

## 工作流程

先按用户请求选择 PRD 或 TDD 阶段，再读取对应的 task.md 并完成其中的工作。起草或审查文档时，按 task.md 的指示读取 document.md；通过完成条件后，按指定路径交付。

## 通用规则

- 给用户提供的信息注明来源；代码结论注明文件、符号或接口。推断和未核实内容标明状态。
- 分开记录事实、假设、建议和决定。只有用户明确确认的结论，才写入正文并记为已决定。
- 只追问会改变目标、范围、验收标准或技术设计的问题，一次问一个。未解决的问题标明状态和影响。
- PRD 确认产品问题和预期结果；TDD 设计系统如何满足这些需求。发现需求缺口时，回到 PRD 阶段澄清。
- 只写当前阶段评审所需的内容。修改现有文档时保留无关内容和已有决定；复杂资料用链接引用。
- 保存位置优先使用用户指定路径，其次沿用仓库约定。未指定时，PRD 保存到 `docs/<主题>/prd.md`，TDD 保存到 `docs/<主题>/tdd.md`。没有可写工作区时，在回复中交付 Markdown。
- 状态使用“草稿”“评审中”或“已批准”。只有用户明确批准后才能标为“已批准”；未知的日期、负责人、指标和资源标为待确认。

## 完成条件

PRD 写清用户问题、目标、范围、需求和验收方式；未决事项有状态和影响。TDD 将每项已确认需求关联到设计和验证方式；未决产品问题不能写成已批准要求。
