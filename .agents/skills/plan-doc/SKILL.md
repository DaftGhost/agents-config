# 任务规划文档

## 选择交付物与模板

阅读用户输入、已有文档和相关实现，选择能支撑评审和验收的最小文档量级：

| 文档量级 | 选择依据 | 交付物与结构 |
| --- | --- | --- |
| 轻量 | 单一场景或局部变更，沿用现有规则，无需独立展开高影响决策 | 一份方案，合并需求、实现、验证与交付安排；读取 [轻量流程与模板](reference/lightweight.md) |
| 常规 | 完整功能，涉及多个场景或模块，有明确的规则、依赖和失败分支 | 按需求或技术阶段使用 PRD、TDD 常规模板 |
| 深入 | 跨系统或多角色，存在复杂状态、重要依赖、迁移，或数据、安全、兼容等高影响决策 | 使用阶段的深入模板，分章展开关键边界、流程、风险和交付安排 |

常规和深入任务按当前阶段读取 [PRD 流程](reference/prd/task.md) 或 [TDD 流程](reference/tdd/task.md)。同时需要两者时，先梳理需求，再以已确认需求为设计基线；进入下一阶段时再加载该阶段资料，两份文档可分别选择量级。

按动作执行：创建按所选流程形成草案；修改只执行受影响步骤并检查关联内容；审查读取 [审查流程](reference/review.md)，所选流程仅用于核对阶段约束和证据来源，不执行形成方案或改写文档的动作。

参考文件按动作加载：流程说明执行顺序，`document.md` 说明内容要求，`template-*.md` 只提供结构。流程中的读取条件满足时再加载对应文件，已加载内容直接复用；局部修改和定向审查只读取相关内容要求，全面审查读取完整规范。

用户指定的交付物、路径、篇幅、结构及仓库强制模板优先。轻量 PRD 或 TDD 取共享轻量模板中请求涉及的内容；明确要求分文档时，将需求放入 PRD，实现与验证放入 TDD，通过需求编号和文件引用关联，不另建合并文档。局部修改保留原文件、结构、编号和无关内容。仅请求口头建议、任务拆分或直接改代码时，不主动创建规划文档。

- 篇幅为参考，以关键规则、失败结果、证据和验证方式是否齐全为准。章节和表格可合并；不适用或超出范围的内容简述原因，详细资料用链接引用。
- 复杂度集中在一处时只展开该节；结构无法表达关键边界时升级量级，并更新引用，避免冲突版本。篇幅受限时说明未覆盖的影响。
- 文档量级取决于需求与技术复杂度，提问量取决于未决决策，信息缺失标明未知。
- 审查按内容覆盖判断；跨模板引用使用章节名或实际位置。

## 按任务调整提问量级

先区分缺口：已有答案直接沿用；客观事实缺失先自行查证，无法核实则标为待核实；需要选择目标、规则或取舍的才列为待决策。两者同时存在时分别记录，并注明事实缺口对选择的影响。日期、负责人等不影响当前决策的信息留占位。仅当待决策项会改变目标、范围、验收或设计时，读取 [提问细则](reference/questions.md)，据此安排问题数量和批次；信息充分时直接继续。

## 证据与决策

- 结论注明来源；代码结论定位到文件、符号或接口。区分事实、假设、建议和决定，推断及未核实信息标明状态；未知日期、负责人、指标和资源保留待确认。
- 需求使用稳定编号，注明来源、确认状态和可观察的验收条件。状态为“已确认”“待用户确认”或“待核实”。可基于证据提出完整的推荐主方案，正文、图表与追踪表统一标为“建议／待评审”；只有用户明确确认的结论才转为已确认决定，并回填关联内容及决策记录。
- 分开记录待用户决策、事实核验与已确认决定；已接受风险单列。未决项注明影响、阻塞环节、依据及后续安排（责任人、时点或触发条件；未知则标明）。
- 先明确产品问题和预期结果，再设计实现；发现需求缺口时更新需求来源。规划工作的修改范围限于文档，代码、配置、数据和测试的修改须有用户另行授权。

## 文档状态与批准条件

轻量方案、PRD 和 TDD 逐份判定状态：

| 状态 | 条件 |
| --- | --- |
| 草稿 | 核心需求或关键设计不清，无法有效评审；保留已知内容和缺口 |
| 评审中 | 内容足以评审，尚待评审或批准；影响批准范围、规则或验收的选择未确认时，标为阻塞批准 |
| 已批准 | 用户明确批准可评审的当前版本及范围，且无阻塞批准的待决策项；文档信息记录获批版本、范围、依据和保留项 |

只有用户明确确认暂缓安排及本次批准边界或临时规则，未决项才可标为不阻塞批准；影响较小、未回答或 Agent 推荐均不能代替确认。原问题继续留在未决清单，暂缓决定另记并关联原问题。文档批准不自动确认未决需求或候选方案；它们不能作为后续设计或实施的已批准输入。

修改已有文档时，核对变更是否影响原批准覆盖的需求、验收或设计结论：有影响则保留旧版批准依据，新版本重新判定状态，可评审时为“评审中”，核心内容不清时为“草稿”；新的批准只覆盖用户本次明确确认的版本与范围。纯排版或链接修复等不改变结论的修改，记录其性质并保留原批准依据。

## 复核与交付

逐项检查当前交付范围适用的内容要求，确认需求、设计和验证通过编号或明确引用关联，正文、图表和决策记录一致；未决项的阻塞判断、需求或设计状态与批准依据相符。验证方案与实际执行结果分开，文档获批或写好方案均不代表实现、测试或发布完成。

保存位置依次采用用户指定路径、仓库约定或已有文件。未指定时，轻量方案为 `docs/<主题>.md`，PRD 为 `docs/<主题>/prd.md`，TDD 为 `docs/<主题>/tdd.md`；无可写工作区时在回复中交付 Markdown。

交付时说明文档位置、未决项及影响、阻塞环节和未执行的验证；无未决项时写“无”。
