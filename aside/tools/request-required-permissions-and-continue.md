## Request Required Permissions and Continue

When a Bash command or tool call needed for the task is blocked by sandbox or agent permissions, use the available approval mechanism to obtain the required execution permission, retry the operation, and continue the task. An initial denial under restricted permissions is not a terminal task blocker while an allowed escalation path remains. Diagnose the cause only far enough to choose the correct next action.

1. Inspect the tool response, exit status, and relevant diagnostics to distinguish a normal command or application result from a sandbox restriction or an agent permission restriction. For example, `rg` returning status 1 means no matches and does not require escalation. A generic “permission denied” message alone does not identify the boundary; use a narrow permitted diagnostic if needed to select the remedy.
2. When the evidence points to a sandbox or agent permission restriction, check the current environment's escalation rules and available approval mechanism. If escalation is allowed and the operation is within the user's authorized task, submit the request to execute the specific operation with the required permission or outside the sandbox. Take this action rather than merely describing the restriction, recommending that the user run the command, or ending the task. State the operation, required access, reason, and material effects; redact secrets and request only the additional permission needed.
3. Use the environment's approval flow and execute the operation once permission is granted. Check for partial effects before retrying an operation that could duplicate a write or external action. Do not substitute `sudo` or another tool for the required approval mechanism.
4. Inspect the retry's result, verify the intended effect, and resume the remaining task. Approval, dispatch, and successful execution are intermediate steps; completion depends on the task's actual success criteria.
5. If escalation is unavailable or prohibited, or an approval request is rejected, follow any permitted review or alternative execution path and continue unaffected work. Report an unresolved blocker only after the applicable permitted paths are unavailable or exhausted, with the specific action, restriction, and required user intervention. Respect explicit denials; do not bypass them through another tool or repeat the same rejected request without new evidence or authorization.

Complete this recovery when the required operation has run with permitted access, its effect has been verified, and task execution has resumed, or when no applicable permitted recovery path remains and the precise blocker has been reported. Classifying the failure alone does not complete recovery.
